# 面镜 MockMirror · Prompt 设计

## 1. 原则

1. **只让模型做擅长的部分**：追问措辞、点评、示范改写交给模型；是否追问、下一题是谁、给多少分由状态机和权重决定。
2. **事实来自简历**：Prompt 中明确禁止编造公司、项目、数字；示范回答只能重组已有事实。
3. **一次只问一个问题**：面试官回复限 100 字，避免模型一口气抛出五个问题。
4. **JSON 必须可降级**：所有结构化输出都有校验与本地兜底，不把产品可用性押在模型稳定性上。
5. **不向候选人泄露评分**：面试官人格 Prompt 明确禁止说分数、禁止跳出角色。

## 2. 面试官系统 Prompt

模板位置：`server/agent/prompts.js → interviewerSystem()`

变量：

| 变量 | 来源 | 预算 |
| --- | --- | --- |
| `persona.name / focus / tone / description` | `content/personas.json` | ~200 字 |
| `profile.name` | 简历解析 | — |
| `condenseProfile(profile)` | 结构化画像 | 1800 字 |
| `jd.text` | 用户输入 | 600 字 |
| 规则条款 | 固定 | ~300 字 |

核心条款：

```text
1. 全程中文口语，像真人面试官，不要用列表、标题或 Markdown。
2. 每次只说一段话，最多 100 字，并且只问一个问题。
3. 先对上一段回答给一句真实、具体的反馈，但不要打分、不要透露评分维度。
4. 只能围绕简历里真实出现过的经历提问，禁止编造候选人没写过的公司、项目或数字。
5. 追问要抓含糊处（口径、归因、个人贡献、权衡），不要泛泛问“还有吗”。
6. 不要替候选人回答，不要输出面试建议，不要跳出面试官角色。
7. 如果候选人说“不知道”，可以给一个很小的提示，然后把问题拉回可回答的范围。
```

### 每轮用户指令（不直接展示）

```text
【系统指令，不要直接复述】
下一步：针对候选人刚才的回答追问。追问内容必须是：「<下一句>」。
先用一句话点出你为什么要追问（例如口径不清、贡献不明、缺少权衡），再自然地问出这个问题。
你刚才对回答的即时判断：稳，主要问题是缺少口径。
候选人已答 2 题，本场计划 6 题。
对话记忆：<memory.summary>
请直接输出你要说的话。
```

把「下一句」写死，是为了让模型只负责**衔接语气**，不负责决定考什么。这样可以避免模型跑题、重复提问、忘记进度。

## 3. 题单规划 Prompt

位置：`planMessages()`

输入：画像 1800 字、JD 900 字、候选题库 24 道（含 id、类别、题干、考察点）。

输出 JSON：

```json
{
  "rounds": [
    {
      "refId": "proj-003",
      "stage": "简历深挖",
      "text": "你在星图证券做的智能问数，最关键的技术取舍是什么？为什么？",
      "intent": "考察技术判断与取舍能力",
      "answerPoints": ["背景与约束", "两条路线对比", "选择原因", "结果与验证"],
      "followUps": ["如果召回率下降，你先动哪一层？", "怎么证明是分流策略带来的提升？"]
    }
  ]
}
```

约束：

- 题量必须等于用户设置；
- 至少一半直接来自简历；
- 优先复用 `refId`，可改写题干但不改考点；
- 禁止编造经历。

校验：题量、`stage` 枚举、题干长度、要点数量；不合法就丢弃该题，用本地题补齐。

## 4. 单题评估 Prompt

位置：`evaluationMessages()`

输入：画像 1400 字、目标岗位、JD 500 字、题目、考察点、参考要点、参考答案（可选）、候选人回答 2200 字。

输出：

```json
{
  "scores": { "structure": 82, "relevance": 86, "depth": 78, "impact": 80, "fit": 84 },
  "verdict": "稳",
  "strengths": ["用具体数字说明了结果", "讲清了评测集构建方法"],
  "risks": ["没有说明 badcase 的分布", "归因的排他性不足"],
  "coaching": "补一句“如何排除其他变量”，可信度会更高。",
  "rewrite": "当时我们先把问题按复杂度分成两类……"
}
```

写作要求：

- `strengths` / `risks` 必须指向具体句子或缺失项，不能写「表达清晰」这种空话；
- `rewrite` 第一人称、120–180 字、只能使用简历已有事实；信息不足时用占位符；
- 温度 0.3，`response_format=json_object`；
- 总分由服务端按固定权重重算，模型只提供分项。

### 校准策略

- 先看方向，再看绝对值：强回答 ≥ 75、可接受 60–74、需要重练 < 60。
- 对「追问」单独放宽结构分：允许 60–120 字的精确回答。
- 若模型分数与本地评分差值 > 25，记录到 `lastError` 便于回归分析（当前仅在开发日志中体现）。

## 5. 复盘报告 Prompt

位置：`reportMessages()`

输入：逐题记录（题目、得分、分项、回答摘要、风险）、JD 缺口、知识库引用。

输出：

```json
{
  "headline": "基础扎实，归因链条还要补",
  "readiness": 78,
  "narrative": "120-180 字整体评价",
  "strengths": [{ "title": "结果表达清晰", "detail": "……" }],
  "risks": [{ "title": "归因论证不足", "detail": "……" }],
  "actions": [{ "title": "为每个结果补一句排他性论证", "detail": "写清还改了什么、怎么排除，练 3 遍。", "kbId": "kb-quantify-impact" }]
}
```

约束：不编造未发生的事；至少 2 条优势、3 条风险、3 条行动；行动必须说明「练什么、怎么练、练多久」。

## 6. 上下文预算

| 部分 | 上限 |
| --- | --- |
| 系统提示 | ~2500 字 |
| 最近消息 | 8 条 |
| 记忆摘要 | 300 字 |
| 单题评估（画像 + JD + 回答） | 4000 字 |
| 报告（逐题摘要） | 6000 字 |

超出时按固定顺序截断：JD → 画像 → 历史回答，保留题目、考察点、评分要求。

## 7. 失败与降级

| 失败 | 处理 |
| --- | --- |
| 401 / 403 | 提示 Key 无效，保留本地模式 |
| 404 | 提示检查 Base URL / 模型名 |
| 429 / 5xx | 单次重试后降级本地；报告保留上次结果 |
| 超时（90s） | 中断请求，降级本地，前端提示 |
| JSON 不合法 | `extractJson` 兼容代码块；仍失败则丢弃该字段 |
| 流式中断 | 已输出文本保留，缺失部分用本地模板补齐 |

## 8. 不做什么

- 不让模型直接决定「是否追问」：成本高、不稳定、不可解释。
- 不让模型读取完整简历原文：噪声大、token 贵、容易抓错重点。
- 不让模型给最终总分：总分必须可复算。
- 不让模型生成面试官「人格切换」：人格由配置决定，避免一场面试里忽冷忽热。
